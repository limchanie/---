# Аналіз предметної області: турфірма «Voyage»

Лабораторна робота: концептуальна модель «сутність-зв'язок» для бази даних «travel\_agency».

## Етап 1. Опис предметної області

### 1.1. Загальний опис

Турфірма «Voyage» організовує та продає туристичні подорожі. Фірма має кілька офісів у різних містах, у яких працюють менеджери та консультанти. Фірма пропонує готові тури: кожен тур має країну, дати початку й завершення, ціну та обмежену кількість місць і **обов'язково включає проживання в певному готелі**. Окрім цього, клієнт може забронювати **лише готель без туру**.

Усі бронювання оформляють працівники фірми. Клієнти можуть мати персональну знижку. База даних потрібна, щоб вести облік офісів, працівників, клієнтів, готелів, турів і бронювань, контролювати оплату та аналізувати продажі.

### 1.2. Аналіз вимог до бази даних

**Питання 1. Для яких типів задач проєктується БД?**

Для п'яти типів задач:

1. Інформація про офіси фірми.
2. Інформація про працівників.
3. Інформація про клієнтів.
4. Інформація про тури та готелі.
5. Інформація про бронювання та оплату.

**Питання 2. Якими інформаційними об'єктами характеризуються вибрані задачі?**

- Задача 1: офіси (представництва) фірми.
- Задача 2: особові справи працівників.
- Задача 3: персональна інформація клієнта.
- Задача 4: два об'єкти: тури та готелі.
- Задача 5: інформація про здійснені бронювання.

**Питання 3. Якою інформацією повинні бути описані ці об'єкти?**

- Офіс: назва, місто, вулиця, будинок.
- Працівник: ім'я користувача, ім'я, прізвище, посада, дата працевлаштування, офіс, керівник, ставка, бонус.
- Клієнт: ім'я, прізвище, стать, дата народження, номер телефону, електронна пошта, знижка.
- Готель: назва, країна, місто, кількість зірок, ціна за ніч.
- Тур: готель, назва, країна, дата початку й завершення, ціна, загальна кількість місць.
- Бронювання: працівник, клієнт, тур або готель, дата бронювання, дати заселення й виїзду, кількість гостей, тип і статус оплати.

**Питання 4. Яким майбутнім запитам мають задовольняти інформаційні об'єкти?**

1. Перелік працівників, які претендують на бонус.
2. Список турів, які недоцільно продавати (низький попит).

### 1.3. Запити користувачів до БД

1. Скільки працівників працює в кожному офісі?
2. Хто яку посаду займає і хто є керівником працівника?
3. У яких містах є офіси фірми?
4. Які тури доступні на певний період?
5. Які напрямки (країни) найпопулярніші?
6. Який менеджер оформив найбільше бронювань?
7. Скільки бронювань зробив певний клієнт?
8. Скільки клієнтів бронювали лише готель без туру?
9. Які готелі найчастіше бронюють?
10. Скільки вільних місць залишилось у турі?
11. Які бронювання ще не оплачені?
12. Який дохід фірми за місяць?

## Етап 2. Опис інформаційних об'єктів і зв'язків між ними

### 2.1. Вибір сутностей

Для БД «travel\_agency» виділено шість сутностей: **office**, **employee**, **client**, **hotel**, **tour**, **booking**.

### 2.2. Атрибути сутностей

Перший атрибут кожної сутності є первинним ключем (позначений жирним). Необов'язкові атрибути позначені словом «необов'язковий».

**office** (офіс)

| Атрибут | Опис |
| --- | --- |
| **office\_id** | унікальний номер офісу |
| office\_name | назва офісу |
| city | місто |
| street | вулиця |
| building\_no | номер будинку (необов'язковий) |

**employee** (працівник)

| Атрибут | Опис |
| --- | --- |
| **employee\_id** | унікальний номер працівника |
| user\_name | унікальне ім'я користувача |
| first\_name | ім'я |
| last\_name | прізвище |
| position | посада |
| employment\_date | дата працевлаштування |
| office\_id | офіс, у якому працює (необов'язковий) |
| manager\_id | керівник, теж працівник (необов'язковий) |
| rate | ставка |
| bonus | бонус (необов'язковий) |

**client** (клієнт)

| Атрибут | Опис |
| --- | --- |
| **client\_id** | унікальний номер клієнта |
| first\_name | ім'я |
| last\_name | прізвище |
| gender | стать (F або M) |
| birth\_date | дата народження |
| phone\_number | номер телефону |
| email | електронна пошта |
| discount | знижка (необов'язковий) |

**hotel** (готель)

| Атрибут | Опис |
| --- | --- |
| **hotel\_id** | унікальний номер готелю |
| hotel\_name | назва готелю |
| country | країна |
| city | місто |
| stars | кількість зірок |
| price\_per\_night | ціна за ніч |

**tour** (тур)

| Атрибут | Опис |
| --- | --- |
| **tour\_id** | унікальний номер туру |
| hotel\_id | готель, який входить до туру (обов'язковий) |
| tour\_name | назва туру |
| country | країна призначення |
| start\_date | дата початку |
| end\_date | дата завершення |
| price | ціна туру |
| seats\_total | загальна кількість місць |

**booking** (бронювання)

| Атрибут | Опис |
| --- | --- |
| **booking\_id** | унікальний номер бронювання |
| employee\_id | працівник, який оформив бронювання |
| client\_id | клієнт |
| tour\_id | заброньований тур (необов'язковий) |
| hotel\_id | заброньований готель без туру (необов'язковий) |
| booking\_date | дата бронювання |
| check\_in\_date | дата заселення (необов'язковий) |
| check\_out\_date | дата виїзду (необов'язковий) |
| guests\_count | кількість гостей |
| payment\_type | тип оплати |
| payment\_status | статус оплати |

**Чому `hotel_id` обов'язковий у `tour`, а в `booking` необов'язкові і `tour_id`, і `hotel_id`.** Тур завжди включає готель, тому в `tour` атрибут `hotel_id` заповнений завжди. У бронюванні заповнюється лише одне з двох полів: якщо бронюється тур, готель береться з самого туру, тому `hotel_id` порожній; якщо бронюється лише готель, заповнений `hotel_id`, а `tour_id` порожній. Так дані не дублюються і не можуть суперечити одне одному.

### 2.3. Зв'язки між сутностями

| Назва зв'язку | Сутності | Тип | Пояснення |
| --- | --- | --- | --- |
| works\_for | employee – office | N:1 | В офісі працює багато працівників, працівник належить одному офісу |
| manages | employee – employee | 1:N | Керівник має багато підлеглих, у кожного працівника один керівник |
| processes | employee – booking | 1:N | Працівник оформлює багато бронювань, бронювання оформляє один працівник |
| makes | client – booking | 1:N | Клієнт робить багато бронювань, бронювання належить одному клієнту |
| includes\_tour | tour – booking | 1:N | Тур може бути в багатьох бронюваннях; бронювання стосується не більше одного туру |
| reserved\_in | hotel – booking | 1:N | Готель може бути заброньований окремо багато разів; бронювання стосується не більше одного готелю |
| includes | hotel – tour | 1:N | У готелі проходить багато турів, тур має рівно один готель |

Зв'язок «клієнт – тур» за суттю є M:N (клієнт може купити багато турів, тур купує багато клієнтів). Його розв'язує проміжна сутність **booking**, так само як сутність `orders` у базі «company».

### 2.4. Кратність зв'язків (мінімум і максимум)

| Зв'язок | Перший бік | Другий бік |
| --- | --- | --- |
| works\_for | employee: нуль або багато | office: нуль або один |
| manages | підлеглий: нуль або багато | керівник: нуль або один |
| processes | employee: рівно один | booking: нуль або багато |
| makes | client: рівно один | booking: нуль або багато |
| includes\_tour | tour: нуль або один | booking: нуль або багато |
| reserved\_in | hotel: нуль або один | booking: нуль або багато |
| includes | hotel: рівно один | tour: нуль або багато |

Біля `tour` у зв'язку `includes_tour` та біля `hotel` у зв'язку `reserved_in` стоїть «нуль або один», бо в бронюванні може не бути туру або готелю.

### 2.5. Обмеження цілісності

1. У бронюванні заповнене **рівно одне** з полів `tour_id` та `hotel_id` (інакше бронювання порожнє або суперечливе).
2. Якщо заповнений `hotel_id`, то `check_in_date` і `check_out_date` теж заповнені, і `check_out_date > check_in_date`.
3. Значення `phone_number` задається рядком за маскою `+380XXXXXXXXX`.
4. Значення `gender` задається одним символом: `F` або `M`.
5. Значення `email` задається рядком за маскою `__@__`.
6. `price > 0`, `price_per_night > 0`, `guests_count > 0`.
7. `stars` має значення від 1 до 5.
8. `end_date ≥ start_date`.
9. `payment_status` має одне зі значень: `paid`, `pending`, `cancelled`.
10. `user_name` працівника та `email` клієнта унікальні.

## Етап 3. ER-модель бази даних «Предметна область»

На ER-діаграмі (файли `domain_er.drawio` та `domain_er.png`) зображено:

- **6 сутностей** (прямокутники з червоною рамкою): office, employee, client, booking, tour, hotel;
- **7 зв'язків** (ромби з синьою рамкою): works\_for, manages, processes, makes, includes\_tour, reserved\_in, includes;
- **48 атрибутів** (овали): office 5, employee 10, client 8, hotel 6, tour 8, booking 11;
- **9 необов'язкових атрибутів** (пунктирні овали): building\_no, office\_id і manager\_id та bonus в employee, discount, а також tour\_id, hotel\_id, check\_in\_date, check\_out\_date в booking;
- **первинні ключі** підкреслені: office\_id, employee\_id, client\_id, hotel\_id, tour\_id, booking\_id;
- **кратність** позначена на кінцях ліній символами «воронячої лапки» (нуль або один, нуль або багато, рівно один).

Сутність `booking` розташована в центрі діаграми, бо вона з'єднує працівників, клієнтів, тури та готелі.
